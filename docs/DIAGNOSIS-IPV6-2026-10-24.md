# Причина отказа сайтов при включённом RED_ROUTE

Дата: 24 октября 2026. Проверена установленная версия 0.1.14, ядро redroute5.
Статус: причина воспроизведена и подтверждена контрольными изменениями временной конфигурации. Производственное исправление не внесено.

## Подтверждённая причина

RED_ROUTE безусловно создаёт TUN с IPv4 и IPv6 и включает автоматические маршруты. На проверенном компьютере это добавляет маршрут `::/0` через RED_ROUTE, хотя у физического подключения нет маршрута в публичный IPv6-интернет. Имеющиеся IPv6-адреса Ethernet — link-local и ULA; они не подтверждают доступность внешнего IPv6.

Chrome обращается к IPv6-адресу Яндекс Музыки. Ядро принимает соединение, определяет TLS-домен `music.yandex.ru`, выбирает правильный для невыбранного сайта выход `direct`, но не может соединиться с IPv6-адресом через физическую сеть. Браузер получает `ERR_CONNECTION_RESET`.

Таким образом, отсутствие сайта в списке означает прямой выход из ядра, но не исключает прохождение пакетов через TUN в режиме «Авто». Именно этот перехват меняет поведение браузера.

Фрагмент локального журнала `artifacts/network-investigation/baseline.log`, один идентификатор соединения:

```text
05:56:34 DEBUG [4145124131 0ms] router: sniffed protocol: tls, domain: music.yandex.ru
05:56:34 ERROR [4145124131 1ms] connection: open connection to [IPv6]:443 using outbound/direct[direct]: dial tcp [IPv6]:443: connectex: A socket operation was attempted to an unreachable network.
```

## Контрольные эксперименты

Проверки выполнялись перезагрузкой одной и той же существующей вкладки Chrome. Профиль и восемь пользовательских правил сохранялись. Настройки роутера, OpenVPN, браузера и расширений не менялись.

| Условие | Результат для Яндекс Музыки |
| --- | --- |
| Установленное приложение, «Выкл» | Страница загружается |
| Установленное приложение, «Авто» | `ERR_CONNECTION_RESET` |
| Возврат в «Выкл» | Страница загружается |
| Временное ядро с исходной конфигурацией Auto и debug-журналом | Ошибка воспроизводится |
| В той же конфигурации удалён только IPv6-адрес TUN | Страница загружается при работающем TUN |
| Возвращена исходная конфигурация с IPv6 TUN | Ошибка возвращается; журнал фиксирует недоступную IPv6-сеть |
| Сохранён IPv6 TUN, но перед sniff добавлен ранний явный отказ IPv6 | Страница загружается |

В последнем эксперименте также перезагружена существующая вкладка 4PDA: открылась настоящая главная страница с новостями. Для 4PDA не выполнена отдельная полная серия повторных сравнений; наиболее подробное подтверждение механизма получено на Музыке.

Проверка обычным .NET HTTPS-клиентом успешно использовала IPv4 и не воспроизводила выбор адреса браузером. Принудительная IPv6-проба возвращала `NetworkUnreachable`; сама по себе она не доказывает момент принятия TCP-соединения. Для объяснения позднего сброса использованы TLS-журнал реального браузерного соединения и код ядра.

## Места в коде

- `src/RedRoute.Core/CoreConfiguration.cs:51`: безусловный IPv6-адрес TUN; рядом `auto_route=true`, `stack=mixed`.
- `src/RedRoute.Platform/DirectNetwork.cs`: перед запуском TUN определяется физический DNS и интерфейс, но не возможность прямого выхода по IPv6.
- `src/RedRoute.Service/TunnelEngine.cs`: настройки физической сети снимаются перед созданием TUN. Вывод ядра сейчас читается без сохранения; поэтому штатный отчёт диагностики не показывал причину отказа этого соединения.
- `vendor/amnezia-box/route/route.go`, `PreMatch` и обработка sniff: предварительный проход останавливается на sniff. Отказ после sniff происходит слишком поздно для проверенного сценария переключения браузера на IPv4.
- Там же, `actionResolve`: разрешение DNS выполняется только при `metadata.Destination.IsFqdn()`. Реальный IPv6-адрес назначения не заменяется IPv4 только потому, что sniff определил домен.
- `.tools/gopath/pkg/mod/github.com/sagernet/sing-tun@v0.7.3/stack_system.go`: ошибка предварительного выбора для IPv6 TCP может сформировать отказ до принятия TCP-соединения.

Установка DNS-стратегии `ipv4_only` сама по себе не закрывает проблему: приложение может получить реальный IPv6-адрес из кеша или собственного DNS. Sniff по умолчанию не заменяет IP назначения доменным именем.

## Проверенные направления исправления

Первый диагностический вариант — не создавать IPv6-адрес и маршрут TUN. Он устранил сбой в текущей сети. Нельзя безусловно переносить его на все режимы: при рабочем физическом IPv6 полный VPN не должен допускать обход туннеля, а профили с IPv6 должны сохранять поддержку IPv6.

Второй диагностический вариант — отказ недоступному IPv6 до sniff:

```json
{"inbound":["tun"],"ip_version":6,"action":"reject","method":"default","no_drop":true}
```

Это правило было первым в списке. Оно позволило браузеру использовать IPv4. Это эксперимент, а не готовая универсальная политика: необходимо учесть локальный IPv6, FakeIP `fc00::/18`, выбранные и невыбранные сайты, возможности VPN-профиля и физической сети. `no_drop=true` нужен в этом варианте, чтобы серия отказов не превращалась в молчаливое отбрасывание пакетов.

Исправление должно выбирать поведение с учётом доступности прямого IPv6 и IPv6 через профиль. Сведения о физической сети нужно получать до создания TUN, исключая собственный адаптер RED_ROUTE. Наличие link-local/ULA-адреса нельзя считать доказательством доступа к публичному IPv6; даже наличие глобального адреса и маршрута не гарантирует фактическую доступность сети. Поведение при смене сети также требует проверки.

## Обязательная проверка исправления

- Реальный Chrome: IPv4-интернет при наличии локальных IPv6-адресов; A/AAAA, сохранённые AAAA и собственный DNS браузера. Повторить «Выкл → Авто → Выкл» и проверку полного VPN.
- В «Авто»: невыбранные сайты сохраняют прямой выход; выбранные домены и IP идут через VPN, включая FakeIP.
- Рабочая физическая IPv6-сеть, VPN с IPv6 и VPN без IPv6: доступность сайтов, правильный выход, отсутствие обхода полного VPN через физический IPv6.
- Локальные IPv4/IPv6-ресурсы, DNS и UDP/QUIC; серии соединений не должны превращать быстрый отказ в тайм-аут.
- Смена сети, обрыв профиля, резервный профиль, авария ядра, «Выкл» и восстановление: после остановки не остаются маршруты RED_ROUTE, интернет работает напрямую.
- Существующие автоматические и живые проверки остаются необходимыми, но успешный запрос отдельного HTTP-клиента не заменяет браузерную проверку.

## Завершение диагностики

Временный процесс завершён, временные `investigation-*.json` удалены, процесса amnezia-box и IPv6-маршрута через RED_ROUTE при завершающей проверке нет. Локальная служба ответила `Success=true`, `Mode=Off`, `Phase=Off`.

После просьбы пользователя не перехватывать экран использовались только чтение файлов и запросы состояния; управление браузером и переключение VPN не выполнялись. Журналы и диагностический помощник остаются локально в игнорируемом `artifacts/network-investigation/`. Профильные ключи в этот документ не включены.
