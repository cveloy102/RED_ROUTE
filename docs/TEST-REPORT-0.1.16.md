# Живая проверка RED_ROUTE 0.1.16

Дата: 24 октября 2026. Пользователь установил 0.1.15 и разрешил управление ПК для испытаний. В ходе проверки найдены и исправлены две дополнительные ошибки; установлена и проверена 0.1.16. Ядро — redroute6.

Последующее уточнение: немедленная диагностическая TCP-проба обнаружила, что проверочный порт может открыться до завершения настройки TUN. После ожидания полного старта тот же обычный Windows TCP/TLS-клиент подтвердил оба выхода по журналу. Ожидание полного старта закреплено и в службе в 0.1.17; итоговая приёмка находится в [отчёте 0.1.17](TEST-REPORT-0.1.17.md).

## Найдено и исправлено

### Объявленный IPv6 профиля не означал рабочего IPv6-выхода

На установленной 0.1.15 в «Авто» обе проблемные страницы загрузились. На тех же вкладках Chrome в полном VPN появился `ERR_CONNECTION_RESET`. Временная копия фактической конфигурации с debug-журналом воспроизвела сбой на том же установленном ядре.

Журнал связывает TLS-домен Музыки и отказ IPv6 через VPN одним идентификатором соединения:

```text
router: sniffed protocol: tls, domain: music.yandex.ru
connection: open connection to [IPv6]:443 using outbound/awg[vpn]: connect tcp [IPv6]:443: network is unreachable
```

В профиле есть адреса обеих версий IP, однако реальные IPv6-запросы через VPN не проходят. Прежняя проверка HTTPS выбирала IPv4 и не выявляла это. В 0.1.16 добавлен отдельный аутентифицированный вход проверки с разрешением только AAAA. Он всегда идёт через VPN, включая «Авто» и политику временного IPv4-выхода.

Результат измеряется до захвата трафика, привязывается к профилю и физической сети и определяет политику захвата. IPv4 остаётся рабочим, даже если IPv6 недоступен. Рабочий IPv6 проверяется каждый цикл; недоступный повторно проверяется через минуту. Изменение результата перестраивает подключение в том же цикле, не дожидаясь трёх ошибок IPv4.

На рабочем профиле установленная 0.1.16 получила два успешных IPv4 HTTPS 204 и два отказа IPv6. Фактическая конфигурация переключилась на `ipv4_only` и ранний отказ недоступного публичного IPv6; профиль остался прежним.

### Список профилей раскрывал конфигурацию через доступность

Генерируемый C# record.ToString включал Config, а WPF использовал его для имени элемента списка в дереве доступности. У VpnProfile переопределён ToString без конфигурации; строковое представление строки интерфейса содержит только видимый заголовок. JSON-передача конфигурации по защищённому IPC сохраняется.

Проверка настоящего WPF automation peer с синтетическим маркером ключа прошла. На установленной 0.1.16 системное дерево реального профиля показывает только его заголовок, без Config и ключей.

## Выполненные проверки

- 532 автоматические проверки приложения и изолированного WG/AWG-стенда прошли. Добавлены отдельный IPv6 health-вход для невыбранного домена, отказ IPv6 HTTP при продолжающем работать IPv4, восстановление IPv6 и изменение возможностей во время успешной IPv4-проверки.
- 122 сценария настоящего предварительного маршрутизатора проверены для TCP и UDP по 100 раз: 24 400 вызовов. Включён профиль с IPv6 в конфигурации, но отрицательным результатом реальной проверки.
- Go-проверки FakeIP, кеша, маршрутизатора и AWG, включая upstream packet/handshake/up-down/concurrency, прошли.
- Полная сборка и 18 проверок MSI прошли. Живое обновление 0.1.15 → 0.1.16 завершилось MSI-кодом 0. Приложение и служба имеют версию 0.1.16, профиль и правила сохранены.
- WPF smoke-тест прошёл; его намеренный сбой завершился ожидаемым ненулевым кодом. Получены изображения приветствия, прогресса и завершения установщика в тестовом режиме без дополнительной установки.
- 24 живые проверки установленного приложения прошли: «Выкл», полный VPN, пустой список «Авто», доменное/IP-правило, изменение резервов без лишнего перезапуска, недоступный основной, отключённый резерв, все профили недоступны, авария ядра, быстрые команды, восстановление, устаревшее обновление, авария службы, её автоматический запуск и сохранность пользовательских данных.
- Дополнительные 10 проверок повторных аварий прошли: три принудительных завершения именно установленного ядра без новых FakeIP-выделений между ними; старый DNS-адрес сохранил работоспособность, новый не занял его место.
- Крестик скрыл окно в трей, процесс и VPN продолжили работу. Отдельное аварийное завершение интерфейса сохранило процесс ядра службы. Нормальный выход с отключением VPN отдельно через меню трея в этом прогоне не выполнялся; WPF smoke проверяет скрытие и повторное открытие.
- В установленном интерфейсе проверены пустой каталог по нажатию, ввод `dis`, подсказки сервисов/доменов, отсутствие скрытой 18+ категории, видимость расширенных настроек после раскрытия, стилизованные импорт и подтверждение удаления. Импорт и удаление отменены; реальный профиль не менялся.

## Браузер и фактический выход

Сравнения выполнялись на одних и тех же вкладках Chrome, без очистки браузерного кеша.

| Условие | Музыка | 4PDA |
| --- | --- | --- |
| 0.1.15, «Авто» | Обычный интерфейс | Полная страница новостей |
| 0.1.15, «Вкл» | ERR_CONNECTION_RESET | ERR_CONNECTION_RESET |
| 0.1.16, «Вкл» | Ответ самого сайта о недоступности в регионе | Полная страница новостей |
| 0.1.16, «Выкл» | Обычный интерфейс | Полная страница новостей |
| 0.1.16, возврат в «Авто» | Обычный интерфейс | Полная страница новостей |

Профиль Музыки показывает предложение оформить Плюс. Подписка не оформлялась; полноценное проигрывание трека не подтверждено. Региональный ответ в полном VPN — не успешное воспроизведение и не сброс соединения. Отдельный HTTP-клиент получал от 4PDA 403; это не подменялось утверждением об успешной браузерной загрузке.

В раннем живом прогоне внешний IP прямого выхода совпадал с IP VPN, поэтому сравнения по IP сами по себе не доказывают селективную маршрутизацию в этой сети. Пользователь сообщил об изменениях маршрутов на роутере и сохранении маршрутов ChatGPT для связи с агентом. Настройки роутера и OpenVPN агент не менял.

Дополнительная проверка использовала временную debug-копию конфигурации, созданной установленной службой, и то же установленное ядро. К исходным правилам временно добавлен example.org; правила ChatGPT сохранены. Реальные запросы Chrome успешно загрузили example.org и example.net. По связанным идентификаторам соединений ядро выбрало `route(vpn)` для выбранного сайта и `outbound/direct[direct]` для невыбранного. Также зафиксирован QUIC выбранного сайта. После проверки исходные настройки восстановлены, временный защищённый JSON удалён.

## Восстановление и локальные материалы

Восстановлены исходные «Авто», один профиль и восемь правил. Канонические машинные настройки совпали с защищённым снимком до испытаний; пользовательский DPAPI-файл сохранился побайтно. После восстановления не обнаружено событий самопроизвольной перестройки сети. Одновременно остаётся один установленный процесс ядра.

Локальные материалы находятся в игнорируемом `artifacts/`: `checks/build-0.1.16.log`, `checks/ui-0.1.16.log`, `checks/install-0.1.16.log`, `checks/live-0.1.16.log`, `checks/live-acceptance.json`, `checks/cached-dns-0.1.16.log`, `checks/cached-dns-regression.json`, `checks/restored-0.1.16.json`, `route-proof/result.json`. Полные установочные журналы и пользовательские данные в публичный репозиторий не включаются.

## Границы

Чистые Windows 10/11, физическая смена подключения, сон/пробуждение, перезагрузка и другая учётная запись UAC не проверены. Резерв проверен заведомо недоступной копией конфигурации и рабочим профилем; это не два независимых реальных сервера. Рабочий внешний IPv6 положительно проверен на изолированном стенде, а не на текущем провайдере/VPN-сервере. Версия остаётся предварительной.
