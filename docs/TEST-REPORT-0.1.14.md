# Проверка RED_ROUTE 0.1.14

Дата: 24 октября 2026. Продолжение [проверки 0.1.13](TEST-REPORT-0.1.13.md).

## Найденные ошибки

### Повторная авария ядра теряла ранее выданные DNS-адреса

На установленной 0.1.12 живой тест воспроизвёл отказ обращения по ранее полученному FakeIP после аварии ядра. Соединение с VPN восстанавливалось, новые адреса выдавались, но запрос по старому адресу получал отказ соединения.

В реальном файловом хранилище amnezia-box чтение метаданных удаляло сохранённый указатель. Если после запуска использовались только уже существующие записи, новое выделение адреса не происходило и указатель не записывался заново. Последующий аварийный перезапуск считал кеш несовместимым и сбрасывал его. Прежние тесты с имитацией хранилища не моделировали удаление при чтении.

Новый Go-тест открывает настоящий файл четыре раза и использует ранее записанное соответствие, без штатного сохранения указателя между открытиями. До исправления он падает на втором открытии; после изменения чтения на недеструктивную транзакцию проходит. Ядро: `1.260910.0-redroute5`.

### Установщик мог пропустить часть встроенной среды при обновлении

Первое реальное обновление 0.1.12 → 0.1.14 завершилось MSI 1603 / service 1920. Windows откатила обновление, исходная служба запустилась, пользовательский DPAPI-файл остался побайтно прежним.

Журнал Windows зафиксировал отсутствие `hostpolicy.dll` при запуске новой службы. Локальная сборка включала .NET 10.0.12, а старая установленная версия — 10.0.13. Windows Installer исключал некоторые компоненты при планировании установки, затем удалял их вместе со старым продуктом. Для частной среды приложения добавлен `REINSTALLMODE=amus`; все три self-contained публикации закреплены на .NET 10.0.13. Проверки MSI дополнены этим свойством и наличием hostpolicy, hostfxr, coreclr и System.Private.CoreLib отдельно для приложения и службы.

Описание свойства: [документация Microsoft](https://learn.microsoft.com/en-us/windows/win32/msi/reinstallmode).

Повторное реальное обновление исправленным MSI завершилось кодом 0. Установлены приложение и служба 0.1.14, ядро redroute5. Пользовательский файл настроек остался побайтно прежним. Приложение после проверок запущено в трей.

## Результаты на исправленной версии

- 371 автоматическая проверка, включая изолированный обмен настоящих WG/AWG-клиента и сервера, прошла.
- Go: fakeip, реальный файловый кеш, AWG-конфигурация и выбранные upstream-тесты пакетов, handshake, up/down и concurrency прошли.
- 18 проверок структуры MSI прошли; пакет содержит обе частные среды запуска.
- WPF smoke-тесты приложения и установщика прошли. Намеренная ошибка smoke-теста завершилась ожидаемым кодом 1.
- 24 живые проверки установленной 0.1.14 прошли: «Выкл», полный VPN, «Авто» с пустым списком, доменным и IP-правилом; сохранение прямого выхода для невыбранного адреса; резерв при недоступном основном профиле; прямой интернет при недоступности всех; авария ядра; сохранение старого DNS-адреса; быстрые команды; восстановление; устаревшее фоновое обновление; авария службы и её автоматический запуск.
- Отдельный живой прогон повторных аварий: 10 проверок прошли, включая три завершения установленного ядра без новых DNS-выделений между ними.
- Исходный режим «Авто», профили и 8 правил восстановлены. OpenVPN не переключался.

Машинные результаты сохранены локально в `artifacts/checks/live-acceptance.json` и `artifacts/checks/cached-dns-regression.json`. Полные установочные журналы остаются локальными; в публичный репозиторий они не включаются.

## Сайты и браузер

В исходном «Авто» было 8 правил. 4pda.to и music.yandex.ru не совпадали ни с доменными, ни с IP-правилами. Проверка системного DNS и прямых DNS-запросов с привязкой к физическому интерфейсу проходила.

В режимах «Авто», «Выкл» и «Вкл» проверочный HTTPS-клиент с отключённым системным прокси полностью получал ответы: Яндекс Музыка — HTTP 200, 4PDA — HTTP 403; example.org — HTTP 200. Ответ 403 не считается успешной загрузкой сайта для человека.

В доступном Chrome загрузка Яндекс Музыки давала ERR_CONNECTION_RESET как в «Авто», так и при полностью выключенном RED_ROUTE и в полном VPN. 4PDA давал ту же ошибку при выключенном RED_ROUTE. Контрольный example.org также дал ERR_CONNECTION_RESET в полном VPN. Это показывает расхождение браузерного и проверочного запросов; точная причина браузерного сброса пока не установлена. Настройки браузера, расширения, антивирус, роутер и OpenVPN не изменялись.

## Границы проверки

Чистые Windows 10/11, вход другим администратором в UAC, сон/пробуждение, перезагрузка и физическая смена сети остаются отдельными непроверенными сценариями. Проверка резерва на рабочем компьютере использует заведомо недоступный тестовый адрес и копию существующего рабочего профиля; это не два независимых реальных сервера. Версия остаётся предварительной.
